## 1. Data-model decision + reconciliation (04 §2 vs the OpenAPI contract)

**Decision: a DISTINCT `onboarding_application` entity** — a resumable, pre-auth
DRAFT — NOT the Member-in-PENDING_KYC.

Why, and how it reconciles:

- **04 §2.2 does not define an onboarding entity.** It carries onboarding
  save/resume state on E-1 Member via the `onboarding_state` JSON field
  (04 §2.2, line 140: "Save/resume step state + KPI-1.1 instrumentation
  timestamps") and drives progression through `MembershipStatus`/`KycStatus` on
  the Member. §2.1 F-A (line 82) does describe onboarding in prose: "the
  applicant starts an onboarding application ... saved server-side and
  resumable."
- **The OpenAPI contract (`schemas/ep1-identity.yaml`) DOES model a distinct,
  pre-auth resource.** `POST /onboarding/applications`
  (`OnboardingApplicationCreateRequest` → `...CreateResponse`) mints an
  `application_id` + `resume_token` and returns `kyc_status = NOT_STARTED`
  BEFORE any authenticated Member (or OIDC subject) exists; `PATCH .../current`
  (`OnboardingApplicationPatchRequest`) carries provisional DEC-6 identity
  fields; `registration_number` is documented as provisional (the KYC-verified
  value is authoritative, DEC-6(d)).
- **The tension, and its resolution.** Modelling onboarding as a
  Member-in-PENDING_KYC would require inserting a Member row at the pre-auth
  bootstrap (applicant has supplied only email + phone + channel code, and no
  IdP subject yet). A rejected application would then have to delete that Member
  row — which violates **DEC-4** ("no member record reaches a rejected
  membership status") and the audit posture. So the distinct DRAFT is the
  physical realization the contract forces and that F-A's "server-side
  resumable application" describes; it is **promoted to an E-1 Member on KYC
  approval** (a later slice — not built here). The build brief's preferred
  option (distinct resumable draft) is therefore also the 04-faithful one.
- **No invented fields.** Every column maps to a contract property or a DEC-6
  identity field. The one enum this slice introduces
  (`OnboardingApplicationStatus = DRAFT | SUBMITTED`) is **flagged**: neither 04
  nor the contract names a status value set for the onboarding application (the
  contract exposes only `kyc_status`, `current_step`, `progress_pct`). DRAFT /
  SUBMITTED are the two states this slice needs, per the brief's explicit
  example; this is documented in the model docstring, not silently chosen.

Deliberate omissions (documented, not gaps):
- **No stored `kyc_status` column.** KYC is deferred to slice 2 (no ХУР/eKYC
  call in this slice). The CreateResponse's pinned `kyc_status = NOT_STARTED` is
  a constant the service returns; storing it would prematurely introduce a
  `KycStatus` enum type. (Note: the existing `Member` model likewise does not
  yet carry `kyc_status` — it is a minimal scaffold subset of 04 E-1.)
- **`resume_token` stored as `resume_token_hash`** (unique), so a leaked row
  does not yield a usable bootstrap token; the service compares hashes. The
  token is application-scoped only — NOT full auth/MFA (a later slice).

## 2. New table `onboarding_application` — columns & enum

New enum type: `onboarding_application_status` = `('DRAFT', 'SUBMITTED')`.

Columns (all nullability rendered by the mock engine, verbatim):

| column | type | null | source |
| --- | --- | --- | --- |
| `email` | VARCHAR(320) | NOT NULL | CreateRequest (verified contact channel) |
| `phone_number` | VARCHAR(32) | NOT NULL | CreateRequest (E.164) |
| `resume_token_hash` | VARCHAR(128) UQ | NOT NULL | CreateResponse `resume_token` (stored hashed) |
| `ovog` | VARCHAR(120) | NULL | DEC-6 clan (optional) |
| `etsgiin_ner` | VARCHAR(120) | NULL | DEC-6 patronymic |
| `ner` | VARCHAR(120) | NULL | DEC-6 given name |
| `mrz_name_latin` | VARCHAR(120) | NULL | DEC-6 MRZ Latin (KYC-populated) |
| `registration_number` | VARCHAR(10) UQ | NULL | DEC-6, 2 Cyrillic + 8 digits, structural-only |
| `address_line_1` | VARCHAR(255) | NULL | DEC-6 structured address |
| `address_line_2` | VARCHAR(255) | NULL | DEC-6 structured address |
| `city` | VARCHAR(120) | NULL | DEC-6 |
| `region` | VARCHAR(120) | NULL | DEC-6 (aimag) |
| `postal_code` | VARCHAR(32) | NULL | DEC-6 |
| `country` | VARCHAR(120) | NULL | DEC-6 |
| `date_of_birth` | DATE | NULL | PatchRequest |
| `status` | onboarding_application_status | NOT NULL | slice lifecycle (flagged above) |
| `onboarding_state` | JSON | NULL | mirrors E-1 `onboarding_state`; backs Current's current_step/saved_data/progress_pct/kpi_timestamps |
| `id` | UUID PK | NOT NULL | UUIDPrimaryKey mixin |
| `created_at` | TIMESTAMP | NOT NULL | Timestamps mixin |
| `updated_at` | TIMESTAMP | NOT NULL | Timestamps mixin |

**Nullability rationale:** identity/address/dob fields are Optional because the
draft row is created at the pre-auth bootstrap (email + phone + channel code
only) and filled step-by-step by PATCH (whose schema marks every field
optional). NOT-NULL enforcement of the DEC-6 name parts happens at promotion to
Member.

Reused existing patterns: `Base` + `UUIDPrimaryKey` + `Timestamps` mixins,
`Enum(..., name=...)`, `String(n)`, `JSON` — all as elsewhere in identity.py.

## 3. Non-negotiables confirmation

- **No money / no float** — the table has zero monetary columns (check_models
  still reports 49 MoneyMinor columns, unchanged; no Float/Numeric added).
- **No `first_name` / `last_name`** — three-part name only (ovog / etsgiin_ner /
  ner) + mrz_name_latin.
- **registration_number** — VARCHAR(10), unique, structural-only; **no
  check-digit formula invented** (documented in the column comment).
- **No hardcoded tz offset**; timestamps via the mixin (`TIMESTAMP WITHOUT TIME
  ZONE DEFAULT now()`), consistent with every other table.
- **No ХУР / ledger / money / share-purchase call** — model + migration only.
