## 1. Data-model decision (inherited from T1, re-affirmed)

A **DISTINCT `onboarding_application` DRAFT entity**, not a Member-in-PENDING_KYC.
The contract (`schemas/ep1-identity.yaml`) exposes a *pre-auth* resource that mints
`application_id` + `resume_token` and returns `kyc_status = NOT_STARTED` before any
authenticated Member/IdP subject exists; inserting a Member at that bootstrap would
force deleting it on rejection, violating DEC-4. Full reconciliation is in T1.md §1.
This slice implements to that entity and to the OpenAPI schemas verbatim; it did not
extend the model, the migration, or the OpenAPI spec (implemented to the existing
contract — no gap found).

## 3. Endpoints — contract conformance

Router prefix `/api/v1/onboarding` matches the contract paths exactly.

| Operation | Method + path | Request schema | Response schema | Status |
| --- | --- | --- | --- | --- |
| `createOnboardingApplication` | POST `/applications` | `OnboardingApplicationCreateRequest` (email, phone_number, channel_verification_code) | `OnboardingApplicationCreateResponse` (application_id uuid, resume_token, steps[], kyc_status) | **201** (per the contract's INFERRED-201 note) |
| `getCurrentOnboardingApplication` | GET `/applications/current` | — (bearer resume token) | `OnboardingApplicationCurrent` (application_id, current_step, saved_data, progress_pct, kpi_timestamps) | 200 |
| `updateCurrentOnboardingApplication` | PATCH `/applications/current` | `OnboardingApplicationPatchRequest` (DEC-6 identity fields, all optional) | `OnboardingApplicationPatchResponse` (current_step, validation_results[]) | 200 |

Pydantic I/O models mirror the OpenAPI schemas (property names, required fields).
Pinned literals honoured: create returns `kyc_status = "NOT_STARTED"` (typed
`Literal["NOT_STARTED"]`). `mrz_name_latin` is intentionally absent from the PATCH
model — it is KYC-populated, never client-supplied (DEC-6).

Error mapping (rendered as the uniform `Error` envelope):
- Missing/malformed bearer token → **401 UNAUTHENTICATED** (both GET and PATCH).
- GET, token resolves to no draft → **404 NO_APPLICATION** (the contract's semantic
  for "applicant has no in-progress application").
- PATCH, token resolves to no draft → **401** (PATCH's contract error set has no 404;
  a non-resolving credential is unauthenticated). Documented asymmetry, contract-driven.
- PATCH invalid `registration_number` shape → **422 VALIDATION_FAILED** (+ `details[]`).
- PATCH on a non-DRAFT application → **409 STATE_CONFLICT** (guard; DRAFT→SUBMITTED is
  the KYC hand-off, a later slice).
- create with a blank channel code → **422 CHANNEL_UNVERIFIED**.

Deferred (NOT built, per brief): checkOnboardingEligibility, createKycSession,
getKycStatus, MFA/step-up, devices, profile, consents. No ХУР/ledger/money/share call.

## 4. Bootstrap-token approach + security note

`create` mints an opaque, application-scoped token via `secrets.token_urlsafe(32)`,
returns the RAW token to the caller exactly once, and persists **only its SHA-256
hash** in `resume_token_hash` (T1's unique column). `get`/`patch` present it as
`Authorization: Bearer <resume_token>`; the service re-hashes and looks the draft up
by hash. Transport (`Bearer`) is the INFERRED carrier the contract's ep1 note pins as
the applicant session (04 §3.0 requires a token but does not pin its transport;
`memberOAuth2` is also `Authorization: Bearer`).

Security note / limits (documented, not hidden):
- SHA-256 (single pass, no salt/KDF) is appropriate here because the token is a
  high-entropy random capability token, NOT a low-entropy password. A leaked DB row
  yields only the hash, never a usable token.
- This is deliberately **NOT the full OAuth2/OIDC + MFA/step-up stack** (memberOAuth2,
  stepUpAssertion) — that is a later slice. No JWT/session infrastructure was built.
- `correlation_id` in the error envelope is currently minted per-response; reading it
  from an inbound tracing header is a later concern.
- Channel verification is a STUB this slice: a present, non-blank `channel_verification_code`
  is accepted as proof of channel control (blank → 422). Real OTP verification deferred.
- `409 APPLICATION_EXISTS` (create dedup by channel) is NOT implemented: with no member/
  channel registry yet, the token is the only handle; per-email dedup is a later slice.

## 5. Tests (`tests/test_onboarding.py`, 7 tests)

No real DB: in-memory SQLite created inside the fixture, `StaticPool` (one shared
connection so commits persist across request-scoped sessions), `get_session`
overridden. Only the `onboarding_application` table is created (`Table.create`) — it
has no FKs, so SQLite never sees the Postgres-specific DDL of other models. Production
code stays Postgres/psycopg.

1. `test_create_returns_201_application_id_and_resume_token` — 201, valid uuid, token, `kyc_status == NOT_STARTED`, `steps` list.
2. `test_get_with_token_returns_draft` — 200, `current_step == IDENTITY`, empty `saved_data`, `progress_pct == 0.0`.
3. `test_update_saves_dec6_field_and_get_reflects_it_resume` — PATCH `ner`/`registration_number`, then a FRESH GET (new session) reflects them → proves resume.
4. `test_missing_token_is_rejected_401` — GET and PATCH with no Authorization → 401.
5. `test_bogus_token_get_is_404_no_application` — GET with a non-matching token → 404, `error.code == NO_APPLICATION` (also asserts the uniform envelope).
6. `test_invalid_registration_number_shape_is_422` — PATCH `"12345678"` (no Cyrillic prefix) → 422, `error.code == VALIDATION_FAILED`.

(Registration validity uses a real Cyrillic value, `УБ12345678` = 2 Cyrillic letters +
8 digits; regex `^[Ѐ-ӿ]{2}[0-9]{8}$`, STRUCTURAL only — no check-digit invented.)

## 6. Non-negotiables confirmation

- **No money / no float in any money path** — this slice touches no monetary field
  (`check_models` still 49 MoneyMinor columns, 0 Float/Numeric). `progress_pct` is a
  presentation percentage, not money.
- **No `first_name`/`last_name`** — three-part name only (ovog / etsgiin_ner / ner).
- **registration_number** — structural regex only; check-digit algorithm never guessed.
- **No hardcoded tz offset** — UTC used only as the storage standard for KPI timestamps
  (`datetime.timezone.utc`); local-tz display is a presentation concern.
- **No ХУР / eKYC / ledger / money / share-purchase call.**
