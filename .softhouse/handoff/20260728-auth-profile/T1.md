## 2. The verifier / port design

`TokenVerifier` is a `runtime_checkable` `Protocol` with one method:
`verify(token: str) -> dict[str, Any]`, which MUST raise `TokenInvalid` on any failure
and MUST NOT return unverified claims. This mirrors the eKYC provider-port pattern: the
concrete IdP key source is a swappable seam.

`JwtTokenVerifier` is the concrete RS256 implementation bound to a configured IdP
**public** key (PEM, SubjectPublicKeyInfo/X.509). It is provided to routes via the
`get_token_verifier` FastAPI dependency, so tests inject a verifier bound to the dev
signer's public key with `app.dependency_overrides[get_token_verifier] = ...`.

The single decode call is:

```python
jwt.decode(
    token,
    key=self._public_key_pem,
    algorithms=list(ALLOWED_ALGORITHMS),   # == ["RS256"], passed EXPLICITLY
    issuer=self._issuer,                   # enforced only when configured
    audience=self._audience,               # enforced only when configured
    leeway=self._leeway_seconds,
    options={
        "require": ["exp"],                # a token with no exp is never accepted
        "verify_signature": True,
        "verify_exp": True,
        "verify_nbf": True,
        "verify_iat": True,
        "verify_iss": self._issuer is not None,
        "verify_aud": self._audience is not None,
    },
)
```

Every PyJWT failure (`jwt.InvalidTokenError` and all its subclasses) is caught and
collapsed into one opaque `TokenInvalid`, so the caller renders a single 401 that leaks
nothing about *which* check failed. The token and claims are **never logged** (there is
no logging in the auth path at all).

Key posture decisions:
- `ALLOWED_ALGORITHMS = ("RS256",)` is a **module constant, NOT configuration.** Widening
  it would re-open algorithm confusion, so it must not be operator-tunable. The token
  **header never selects** the algorithm or key class.
- **Fail closed:** if no IdP public key is configured, `verify` raises
  `AuthConfigurationError` (it cannot verify, therefore admits no one). `get_current_member`
  maps that to a 401, never a partial admit. There are no production member routes yet, so
  this has no live impact; a real deployment MUST supply `DCB_AUTH_JWT_PUBLIC_KEY`.
- **JWKS seam (documented, not built):** a production IdP typically publishes a JWKS URL
  with rotation + `kid` selection. That is the natural extension of this port (fetch+cache
  JWKS, pick key by header `kid`, build the equivalent verifier). The no-network foundation
  verifies against a supplied PEM; the algorithm allow-list is unchanged either way.

## 3. `get_current_member` — exact algorithm + claim checks, and the attacks rejected

Flow: `Authorization: Bearer <JWT>` → `bearer_token` (missing/malformed scheme → 401) →
`verifier.verify` → `claims["sub"]` → `MemberRepository.get_by_subject` → `Member`.

**Algorithm enforced:** `RS256` ONLY, passed explicitly to `jwt.decode`.

**Claims enforced:**
- `exp` — REQUIRED (`options.require=["exp"]`) and verified → expired rejected.
- `nbf` — verified when present → not-yet-valid rejected.
- `iat` — verified when present.
- `iss` — verified **only when `DCB_AUTH_JWT_ISSUER` is configured** → wrong issuer rejected.
- `aud` — verified **only when `DCB_AUTH_JWT_AUDIENCE` is configured** → wrong audience rejected.
- `sub` — resolved to a Member row by UUID PK. It is the **only** claim trusted as a member
  fact, and only as a DB key; every other member attribute comes from the DB row.

**Attacks explicitly rejected (each has a NON-VACUOUS test in `tests/test_auth.py`):**

| Attack | How it's rejected | Why the test is non-vacuous |
| --- | --- | --- |
| **`alg: none`** (unsigned forgery) | `"none"` ∉ `ALLOWED_ALGORITHMS` → `InvalidAlgorithmError` → 401 | The token names a real member; a verifier allowing `none` would return 200 (asserted: signature-skipping decode yields the member `sub`). |
| **HS256 / algorithm-confusion (key-confusion)** | `"HS256"` ∉ `ALLOWED_ALGORITHMS` → rejected; the header can never select a symmetric alg / different key class | Token is hand-forged as HS256 using the RSA **public key PEM as the HMAC secret** (PyJWT's own encoder refuses this, so the classic attack token is built by hand). The test asserts the forged HMAC genuinely validates under the confusion, so a naive verifier would return 200. |
| **Expired** (`exp` past) | `verify_exp` → `ExpiredSignatureError` → 401 | Signature is valid and `sub` is a real member — only `exp` fails (asserted: `verify_exp=False` decode admits the member). |
| **Bad signature** (wrong key) | RSA signature check fails → `InvalidSignatureError` → 401 | Signed by a different keypair; payload well-formed and names a real member (asserted via signature-skipping decode). |
| **Unknown / malformed subject** | `get_by_subject` returns `None` (unknown UUID, or `sub` not a UUID) → 401 | A perfectly valid, signed, unexpired token whose `sub` simply isn't a member row. Only the DB lookup rejects it. |
| Missing / wrong-scheme `Authorization` | `bearer_token` → 401 | — |
| Wrong `iss` / wrong `aud` (strict verifier) | `InvalidIssuerError` / `InvalidAudienceError` → 401 | Same token verifies fine against a non-strict verifier (asserted). |
| Not-yet-valid (`nbf` future) | `ImmatureSignatureError` → 401 | — |

**Status choice for unknown subject:** the brief allows 401 **or** 403. This slice returns a
uniform **401 `UNAUTHENTICATED`** for a validly-signed-but-unknown subject (matching the
onboarding router's convention and avoiding member enumeration — the response does not reveal
that the signature was valid). The tests assert `status_code in (401, 403)` so a later switch
to 403 would not break them.

## 4. The dev signer — test-only approach

`DevRsaSigner` generates a fresh RSA-2048 keypair **in memory at construction**. Nothing is
persisted, committed, or exported to prod:
- Guard 1: it raises `RuntimeError` if constructed under `DCB_ENV=production`.
- Guard 2: it is imported **only** by `tests/test_auth.py` (verified: no app module imports it;
  the mentions in `app/auth/__init__.py` are docstring text, not imports).
- The production `get_token_verifier` only ever receives an operator-supplied **public** key
  from `app.auth.config` — never this signer, never a private key.

It exposes `public_key_pem` (feed to the verifier), `private_key_pem` (test signing only),
`verifier(issuer=, audience=)` (build a matching verifier), and `mint(subject, issuer=,
audience=, expires_in_seconds=, not_before=, extra_claims=)`. `expires_in_seconds` may be
negative to forge the expired-token case. No usable production secret exists in the repo.
