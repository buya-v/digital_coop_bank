## 1. Member model extension (E-1) + migration in LOCKSTEP

`app/models/membership.py` — added to `Member` the contract-required
`MemberProfile` fields (reconciled with 04 §2.2 E-1 and the schema
`openapi/schemas/ep1-identity.yaml`):

| field | column | notes |
|---|---|---|
| `member_id` | `VARCHAR(16)` **NOT NULL, UNIQUE** | public non-guessable id, `DCB-XXXXXXXX` (DEC-28) |
| `address_line_1/2`, `city`, `region`, `postal_code`, `country` | nullable | structured postal address |

| `preferred_language` | `VARCHAR(35)` **NOT NULL**, default `mn` | Cyrillic-Mongolian default (CLAUDE.md) |

- **`legal_name` is DERIVED read-only** — a Python `@property` on `Member`
  (`" ".join(ovog, etsgiin_ner, ner)` in Mongolian order), **never a stored
  column**. It cannot be written; attempting to set it → 422.
- No invented fields: MemberProfile's remaining optional properties
  (`date_of_birth`, `joined_at`, `dividend_election`, `kyc_status`,
  `onboarding_state`) are NOT added — none is `required` in the schema and the
  brief's extension list omits them. The response projects only the
  fully-populatable subset.
- **Migration lockstep**: `migrations/versions/0001_initial.py` `CREATE TABLE
  member` updated with the same columns (in SQLAlchemy's emitted order:
  declared columns then the `id`/`created_at`/`updated_at` mixin columns) plus
  `CONSTRAINT uq_member_member_id UNIQUE (member_id)`. DDL was taken verbatim
  from `check_migration.render_model_ddl()` so `check_migration` PASSES.
- Style: new columns use the file's established `Mapped[Optional[str]]` form
  (bare `Optional`, no `| None`) — deliberate for Python-3.9 gate-safety
  (SQLAlchemy evaluates `Mapped[...]`; the project's `/ready` note documents PEP
  604 `|` failing on 3.9). See the ruff note in §6.

## 2. Promotion wiring (services/kyc.py `_promote`) + DEC-4 still holds

## 3. Endpoints — conformance + editable/read-only set

`app/api/routers/members.py` (wired into `app/main.py`), `app/services/profile.py`.

- `getMyProfile` — `GET /api/v1/members/me` → 200 `MemberProfile`; `legal_name`
  DERIVED. `Depends(get_current_member)`.
- `updateMyProfile` — `PATCH /api/v1/members/me/profile` → 200
  `ProfilePatchResponse` (`{profile, reverification_required}`).
  `reverification_required` is True when any editable (name/address/contact)
  field actually changed.

**Editable set** (member-writable): `ner`, `etsgiin_ner`, `ovog`,
`address_line_1`, `address_line_2`, `city`, `region`, `postal_code`, `country`,
`email`, `phone_number`.

**Read-only → 422** (validate-then-apply; a rejected PATCH mutates nothing):

| field | 422 code | why |
|---|---|---|
| `legal_name` | `LEGAL_NAME_NOT_EDITABLE` | derived, not stored |
| `mrz_name_latin` | `MRZ_NAME_NOT_EDITABLE` | KYC-populated verbatim MRZ |
| `registration_number` | `REGISTRATION_NUMBER_NOT_EDITABLE` | identity key; a change needs KYC step-up (out of scope this slice) |
| `member_id` | `MEMBER_ID_NOT_EDITABLE` | system-owned public id |
| `id` | `FIELD_NOT_EDITABLE` | UUID PK |

Unknown fields → 422 `VALIDATION_FAILED`.

**Reconciliation note (registration_number)**: the contract's
`ProfilePatchRequest` schema *lists* `registration_number` as a property, but
the brief/task and the CLAUDE.md non-negotiable require rejecting a change to
it. Resolved by treating a `registration_number` change as needing KYC step-up
(the schema's own header says "KYC-relevant changes require step-up"), which is
an explicitly-deferred slice — so in THIS slice it is not member-editable → 422.
The request model still declares it (mirrors the schema) but the service rejects
it. The PATCH request model uses `extra="allow"` so a client trying to set
`legal_name`/`mrz_name_latin`/`member_id` (fields NOT in the schema) is
DETECTED and 422'd rather than silently dropped.

## 4. IDOR safeguard

Both endpoints derive identity SOLELY from `get_current_member` (verified token
`sub` → DB row). **No member id is read from any path or body** — there is no
`{member_id}` path param and the body carries none. A member can therefore only
ever read/write their OWN profile; the IDOR class is excluded by construction,
not by a check that could be forgotten. Covered by
`test_token_resolves_to_own_profile_only` and
`test_patch_with_a_token_never_touches_b` (A's token leaves B's row untouched).
