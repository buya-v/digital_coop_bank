## 2. The rule engine design (`app/services/eligibility.py`, new file)

Two layers, one file:

- **Pure engine** — `evaluate(answers, ruleset) -> EligibilityOutcome`. No I/O, no
  session; deterministic; unit-testable in isolation. A rule set is plain data:
  `{ version, match: "ALL"|"ANY", rules: [ {id, field, operator, value, remediation} ] }`.
  Operators: `equals`, `in`, `gte`, `lte` (a small, closed registry — `_OPERATORS`).
  - **Missing answer** → the criterion FAILS (applicant ineligible). NOT malformed.
  - **Present but wrong type** for a type-strict operator (`gte`/`lte` require an
    integer) → `EligibilityAnswersInvalid` (422). `float` and `bool` are rejected for
    numeric operators — this upholds the **no-float** non-negotiable even for an age
    comparison, and stops `True`/`False` (an `int` subclass) sneaking through `gte`.
  - A bad rule set itself → `EligibilityConfigError` (programmer/config defect, never
    raised for the shipped default) — guards a future ConfigurationParameter loader.
  - `match: "ALL"` (default) = every rule must pass; `"ANY"` = at least one.
  - `EligibilityOutcome` = `{eligible, failed_criteria[ids], remediation[strings], ruleset_version}`.
- **`EligibilityService`** — orchestration. Reuses the slice-1
  `OnboardingApplicationRepository` and the slice-1 `_hash_token` / `_now_iso`
  helpers (imported — one source of truth for token→hash mapping and UTC format; a
  divergent copy would silently break token resolution). Resolves the draft from the
  bootstrap-token hash, guards the already-passed case, loads the rule set FROM CONFIG,
  evaluates, records the outcome on the draft, and returns it. **Never commits** — the
  router owns the transaction boundary (slice-1 convention); the repo only flushes.

Outcome recording (on `onboarding_application.onboarding_state`, the existing JSON
column — no schema/migration change):
```
onboarding_state["eligibility"]   = { eligible, failed_criteria[], ruleset_version, checked_at }
onboarding_state["kpi_timestamps"]["eligibility_checked_at"] = <iso>
```

## 3. The DEFAULT rule set (config-driven, NOT a hard-coded bond)

Lives in `app/config.py` as `ELIGIBILITY_COMMON_BOND_RULES` (config path
`eligibility.common_bond_rules`), read via `get_common_bond_rules()` which returns a
**deep copy** (the engine cannot mutate the shared default). This function is the single
seam a later ConfigurationParameter-backed loader (US-12.5 — **NOT built here**) replaces.

The specific bond (employer / association / aimag) is NOT chosen (CLAUDE.md blocking
question #1, PO provisional direction). So the default set is **bond-NEUTRAL**: it asks
the applicant to DECLARE which of the three lawful bond categories they claim and to
AFFIRM membership, plus the age-of-capacity floor. It names no specific employer or
aimag. Narrowing `bond_type`'s allowed set (or pinning one value) later is a CONFIG
edit, not code.

`version: "common-bond-default-v1"`, `match: "ALL"`, rules:

| id | field | operator | value | on-fail remediation |
| --- | --- | --- | --- | --- |
| `AGE_OF_CAPACITY` | `age` | `gte` | `18` | must be at least 18 to join |
| `BOND_TYPE_DECLARED` | `bond_type` | `in` | `[EMPLOYER, ASSOCIATION, AIMAG_DISTRICT]` | select the shared common bond |
| `COMMON_BOND_AFFIRMED` | `bond_affirmation` | `equals` | `true` | confirm you belong to the bond group |
