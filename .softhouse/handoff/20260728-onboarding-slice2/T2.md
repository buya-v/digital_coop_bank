## 1. The KYC-before-Member decision + 04/contract reconciliation

`KycSubmission` (E-2, `app/models/identity.py`) has a **NOT-NULL `member_id` FK**,
but KYC runs during the PRE-AUTH onboarding application — **before any Member
exists** (DEC-4: no member record ever reaches a rejected status; a rejected or
abandoned application must leave NO member row). These two facts cannot both hold
in one table, so:

- **In-flight KYC state lives on the DRAFT** (`onboarding_application`), not in a
  `KycSubmission` row: `kyc_inquiry_id` (the eKYC-provider inquiry reference) and
  `kyc_status` (the contract lifecycle enum).
- **The member-linked `KycSubmission` is created only AT PROMOTION** (APPROVED),
  when a Member finally exists — carrying the result/evidence.

**04 reconciliation.** 04 §2.2 models onboarding progression on the E-1 Member
(`kyc_status`, `onboarding_state`), i.e. it assumes a Member row already exists.
That is incompatible with the pre-auth OpenAPI resource (createKycSession returns
`kyc_inquiry_id`/`kyc_status` with no authenticated Member) and with DEC-4. Slice-1
already resolved this by making `OnboardingApplication` a DISTINCT pre-auth draft
entity (see its model docstring); T2 follows the same reconciliation and carries the
in-flight KYC handle on that draft, promoting to the E-1 Member on approval. This is
the physical form the contract forces; it does not contradict 04's field set (every
column maps to a contract property).

## 2. Draft schema extension (model + migration in LOCKSTEP)

`app/models/identity.py`:
- New enum `KycStatus` (`NOT_STARTED, IN_PROGRESS, PENDING_REVIEW, APPROVED,
  REJECTED`) — values **verbatim** from the OpenAPI `KycStatus` schema / 04 §2.2.
- Two columns on `OnboardingApplication`:
  - `kyc_inquiry_id: Mapped[Optional[str]]` `String(128)`, **UNIQUE**.
  - `kyc_status: Mapped[Optional[KycStatus]]` `Enum(name="kyc_status")`.

**Why real columns, not `onboarding_state` JSON** (the brief asked to justify): the
contract RETURNS both fields (createKycSession → `kyc_inquiry_id` + `kyc_status`;
getKycStatus → `kyc_status`). `kyc_inquiry_id` must be **UNIQUE** (it is the E-2
join key at promotion) and `kyc_status` gates a state machine (409
KYC_ALREADY_APPROVED; idempotent promotion) — both want first-class column
semantics (a UNIQUE constraint, an ENUM type) a JSON blob cannot express. The KYC
RESULT/evidence still lands on the member-linked E-2 `KycSubmission`; only the
in-flight handle is columnar. `NULL kyc_status` == NOT_STARTED (no session yet).

**Migration lockstep** (`migrations/versions/0001_initial.py`, the single initial
migration): added `CREATE TYPE kyc_status AS ENUM (...)`, the two columns + the
`uq_onboarding_application_kyc_inquiry_id` UNIQUE constraint to the
`onboarding_application` CREATE TABLE (copied verbatim from the mock-engine render
so normalisation matches), and the matching `DROP TYPE` in `downgrade()`. Statement
count 141 → **142 on both sides**. `check_migration` = PASS.

## 3. eKYC provider PORT + MOCK (`app/adapters/ekyc/`)

- `port.py` — `EkycProvider` (ABC) with `start_verification(applicant)` and
  `get_result(inquiry_id)`; dataclasses `EkycApplicant`, `EkycSession`,
  `EkycResult`; `EkycProviderError` (→ 502 VENDOR_UNAVAILABLE). It is a **ХУР/XYP
  STATE-REGISTER lookup, NOT biometric** — no image/selfie/liveness crosses the
  boundary. The response surface is confined to what the contract + 04 §2.2 name
  (KycSession/KycStatus responses; E-2 `ocr_extracted_fields`/`result_reasons`/
  `evidence_refs`) plus the KYC-verified `registration_number` DEC-6(d) makes
  authoritative — **no ХУР wire-format field is invented.**
- `mock.py` — `MockEkycProvider`: deterministic, in-memory, no network. Outcome is
  a **construction-time toggle** `scripted_status` (the brief's "config toggle"), so
  a caller/test picks the branch: `IN_PROGRESS` (stays pending), `APPROVED`,
  `PENDING_REVIEW`, `REJECTED`. `start_verification` remembers the applicant by
  `inquiry_id`; `get_result` reads it back (so ONE instance must serve create+poll —
  the router/tests wire it that way). `verified_registration_number` override lets a
  test simulate a register value that differs from the provisional one (DEC-6(d));
  `unavailable=True` raises → 502.

**How tests drive every outcome:** the router exposes `get_ekyc_provider` (a FastAPI
dependency returning `MockEkycProvider()` by default — the seam a real ХУР client
swaps into). Tests `app.dependency_overrides[get_ekyc_provider] = lambda: <mock>`
with the scripted status they want; the fixture's `set_provider` shares ONE instance
across the create+poll of a flow.

## 4. Endpoints (to the contract, `ep1-identity.yaml`)

Both added to the existing EP-1 router (`app/api/routers/onboarding.py`); logic in
`app/services/kyc.py` (`KycService`), repos never commit, router commits on mutation
(slice-1 convention).

- **createKycSession** `POST /api/v1/onboarding/kyc/sessions` → **201**
  `KycSessionResponse` (`kyc_inquiry_id`, `session_token`, `kyc_status` pinned
  "IN_PROGRESS"). Starts via the port, stores inquiry id + IN_PROGRESS on the draft.
  409 KYC_ALREADY_APPROVED (draft already APPROVED); 502 VENDOR_UNAVAILABLE; 401.
- **getKycStatus** `GET /api/v1/onboarding/kyc/status` → **200** `KycStatusResponse`
  (`kyc_status`, `retry_guidance`, `pending_review`). Re-polls the port as the
  contract implies; NOT_STARTED when no session; short-circuits APPROVED/REJECTED
  idempotently (no re-poll/re-promote); keeps polling IN_PROGRESS/PENDING_REVIEW.
  It mutates (promotion/status), so the router commits.

## 5. Promotion (the crux) + the explicit DEC-4 guarantee

`KycService._promote` (triggered ONLY from getKycStatus when the port returns
**APPROVED**):
1. Guards that DEC-6 name parts are present (defensive).
2. `registration_number` = the KYC-verified value (DEC-6(d) authoritative) else the
   draft's provisional value.
3. Creates the **E-1 Member**: DEC-6 three-part name (`ovog`/`etsgiin_ner`/`ner`) +
   `mrz_name_latin` + `registration_number`; `membership_status` **PENDING_KYC →
   PENDING_PAYMENT** (born at PENDING_KYC the instant KYC approves, immediately
   advanced). **STOPS at PENDING_PAYMENT.**
4. Creates the member-linked **E-2 KycSubmission** (`member_id`, `kyc_inquiry_id`,
   `NATIONAL_ID`, register fields → `ocr_extracted_fields`, `CLEAR`, `PASSED`,
   reasons/evidence, submitted/resolved timestamps).
5. Marks draft `kyc_status=APPROVED`, `status=SUBMITTED` (frozen).

**DEC-4 guarantee — a Member is created on APPROVED and NOWHERE ELSE.** REJECTED
sets only `draft.kyc_status=REJECTED` (no Member, no KycSubmission); PENDING_REVIEW /
IN_PROGRESS likewise create nothing. **Proving test:
`tests/test_kyc.py::test_status_rejected_creates_no_member`** — drives the mock to
REJECTED and asserts `member_count() == 0` AND `kyc_submission_count() == 0`. (The
PENDING_REVIEW and IN_PROGRESS tests also assert `member_count() == 0`;
`test_approved_promotion_is_idempotent` asserts a second poll does not create a 2nd
Member.)

## 6. Slice-1 leftovers

- **409 REGISTRATION_NUMBER_MISMATCH** — implemented in `OnboardingService.update_step`
  (`app/services/onboarding.py`), the operation the contract declares it on (PATCH
  updateCurrentOnboardingApplication, DEC-6(d)). When a KYC session resolves it
  records the register's authoritative `verified_registration_number` on the draft
  (`onboarding_state.kyc`); a later PATCH supplying a **conflicting** provisional
  value raises `RegistrationNumberMismatch` → router maps to 409. Reachable via the
  PENDING_REVIEW path (which keeps the draft editable; APPROVED freezes it to
  SUBMITTED → STATE_CONFLICT first). Test:
  `test_kyc.py::test_patch_conflicting_registration_after_kyc_verify_is_409`.
  *Note:* the task text placed this "at the promotion transition"; the contract yaml
  attaches the 409 to PATCH, and getKycStatus's declared responses are only
  200/401/429 — so to keep every endpoint within its declared codes it lives on
  PATCH (its DEC-6(d) origin is the KYC-verified value, recorded at resolution).
- **Gap tests** (`tests/test_onboarding.py`): `test_patch_non_resolving_token_is_401`
  (well-formed bearer resolving to no draft → 401 UNAUTHENTICATED);
  `test_create_with_blank_channel_code_is_422_channel_unverified` (blank
  `channel_verification_code` → 422 CHANNEL_UNVERIFIED).
