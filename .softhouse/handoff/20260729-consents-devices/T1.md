## Contract conformance per endpoint

**listMyConsents** — returns `{consent_records[], next_cursor}`. Each record is
the contract `ConsentRecord` shape: `id` (uuid), `consent_type`, `action`,
`version`, `recorded_at` (date-time), `channel`. Accepts `cursor` + `limit`
query params (root.yaml `Cursor`/`Limit`). History is ordered chronologically
(append order), keyset-paginated; `next_cursor` is null on the last page (the
contract marks it nullable/INFERRED).

**upsertMyConsent** — `consent_type` from the path (validated against the
`ConsentType` enum; unknown → 422 VALIDATION_FAILED). Body is
`ConsentUpsertRequest` = `action` + `version` (unknown action / empty version →
422). Per the contract this returns **200 `ConsentListResponse`** (the append-only
history), not a single record — implemented as such. `ConsentRecord` is treated
as an APPEND-ONLY audit row (E-4, confirmed by the schema description and the
model carrying only `recorded_at`, no Timestamps mixin): a grant/withdrawal
APPENDS a new immutable row; nothing is updated or deleted. Withdrawing a
service-required consent → **409 CONSENT_REQUIRED_FOR_SERVICE**.
- `channel`: the audit row requires it (NOT NULL) but `ConsentUpsertRequest`
  does not carry it. Server stamps a default (`MOBILE_APP`) when absent; a caller
  MAY supply `channel` (the request schema does not set additionalProperties:
  false). Flagged for review if a canonical channel vocabulary/source is later
  pinned.
- `SERVICE_REQUIRED_CONSENTS = {TERMS_AND_BYLAWS, PRIVACY_POLICY,
  E_SIGN_DISCLOSURE}` (the mandatory legal/regulatory acceptances). MARKETING,
  DATA_SHARING_OPEN_BANKING, IMPACT_SPOTLIGHT are optional and freely
  withdrawable. This mapping is a documented judgment (04 does not enumerate the
  required set); kept as an explicit frozenset so a config source can replace it.

**listDevices** — returns `{devices[], next_cursor}`; each device is the contract
`Device` shape: `id`, `platform`, `bound_at`, `last_seen_at`. "Trusted devices" =
ACTIVE bindings only; a REVOKED binding is excluded (the `Device` schema has no
status field, so a revoked row has no representation). Accepts `cursor` + `limit`.

## IDOR safeguard (the crux)

Identity comes ONLY from `get_current_member` (verified token `sub` → Member DB
row). NO member id is ever read from a path or a body — `consent_type` and the
future `{id}` name WHICH resource, never WHOSE. Every repository entry point
(`list_for_member`, `latest_for_type`, `append`) takes the owning `member_id` as
a required argument and filters/writes on it, so the data layer cannot be asked
for another member's rows. The class is excluded by construction, not by a check
that could be forgotten — identical to the profile slice.

Non-vacuous test coverage: member B is seeded with DISTINCT consents/devices;
A's token never returns B's rows (`test_list_is_scoped_per_member` in both
suites), and after A issues a hostile write, B's rows are asserted byte-for-byte
unchanged (`test_a_upsert_never_touches_b`). No-token and malformed-scheme →
401.

## DEFERRED for step-up (and why)

- **revokeDevice** `DELETE /api/v1/auth/devices/{id}` — its contract `security`
  is `[{memberOAuth2: [], stepUpAssertion: []}]`, i.e. it requires a fresh
  step-up assertion IN ADDITION to the session. Step-up minting/verification
  (`POST /auth/step-up`, the `stepUpAssertion` scheme) is a later slice, so this
  op is intentionally NOT mounted. `test_revoke_device_is_not_implemented_here`
  asserts the DELETE route resolves to no 2xx. Its 409 LAST_DEVICE rule and the
  `DeviceRevokeResponse` (`status: REVOKED`) belong to that later slice.
- listMyConsents, upsertMyConsent, listDevices are all memberOAuth2-ONLY in the
  contract (no `stepUpAssertion`), so all three were built. upsertMyConsent does
  NOT require step-up per the contract and was therefore NOT deferred.

Also out of scope by contract (EP-1 §3.1 but not this task): createMfaEnrollment,
createStepUpToken, and all onboarding/profile ops (already built in prior slices).
