## The `mfa_factor` model

Columns: `member_id` (FK -> member.id), `factor_type` (enum TOTP/SMS), `status`
(enum PENDING/ACTIVE), `secret_ciphertext` (VARCHAR(512), nullable), `confirmed_at`
(nullable), plus `id` PK and `created_at`/`updated_at` (Timestamps mixin).
Constraint `uq_mfa_factor_member_factor_type` UNIQUE(member_id, factor_type) —
per-(member, type) uniqueness.

Design notes:
- The persisted `mfa_factor_type` enum is **TOTP/SMS only**, even though the OpenAPI
  `MfaFactorType` schema also lists BIOMETRIC. BIOMETRIC is device-local (already
  modelled by `DeviceBinding.biometric_enabled`), not a server-stored secret, so it
  is rejected at the API boundary (422) and never persists. Constraining the DB enum
  keeps it honest about what the server can actually verify.
- `secret_ciphertext` is nullable because an **SMS** factor has no server-stored
  TOTP seed — its one-time code travels out-of-band through the SMS port and is a
  transient verification concern (a T2 detail), not persisted at rest here.
- `confirmed_at` is set by T2 at the PENDING -> ACTIVE promotion; NULL while PENDING.

## Encryption approach (secret at rest) + key-management / KMS caveat

- `app/auth/mfa.py::SecretCipher` wraps `cryptography.fernet.Fernet` — **authenticated**
  symmetric encryption (AES-128-CBC + HMAC-SHA256, integrity-checked on decrypt).
  The service generates a TOTP seed, encrypts it, and stores **only the ciphertext**;
  the plaintext seed exists in memory only long enough to build the one-time otpauth
  provisioning URI, and is never logged, returned afterwards, or persisted.
- Key source: env var `DCB_MFA_ENC_KEY` (a urlsafe-base64 32-byte Fernet key),
  **operator-supplied, never committed / hard-coded / logged**. Resolved via the
  `get_secret_cipher` FastAPI dependency. A missing/malformed key **fails closed**
  (`MfaCryptoNotConfigured`) — enrollment is refused rather than storing an
  unprotected secret; the router-registered handler returns a generic
  `500 MFA_UNAVAILABLE` envelope that never leaks the key or the exception text.
- **KMS / production caveat (documented in the module):** the app-level env key is a
  pragmatic baseline, NOT the production end state. In production the key belongs in
  a KMS/HSM using envelope encryption (a KMS master key wraps per-record/tenant data
  keys; the app never sees raw key material; rotation re-wraps without re-encrypting
  every row). `get_secret_cipher` is the single seam a KMS-backed provider replaces —
  callers only see the `SecretCipher` interface. Data-residency (CLAUDE.md blocking
  Q#3) means the KMS is operator-chosen / in-Mongolia; nothing here assumes a cloud KMS.
- TOTP itself is delegated to **pyotp** (never hand-rolled): `generate_totp_secret`,
  `totp_provisioning_uri`, `verify_totp`. Verification window is **±1 step**
  (`TOTP_VALID_WINDOW = 1`) — small, no wide drift (T2 reuses this bound).

## Binding mechanism (PENDING -> ACTIVE), decided against the contract

The contract exposes only `createMfaEnrollment` (returns `binding_challenge`) and
`createStepUpToken` (T2). There is **no separate confirm endpoint**. Decision:

- Enrollment creates the factor **PENDING** and returns the challenge (TOTP: the
  otpauth URI carrying the seed; SMS: a masked confirmation — see below).
- A factor becomes **ACTIVE only when the member proves a correct code** — the first
  successful step-up verification against that factor, which **T2 performs** (setting
  `status = ACTIVE`, `confirmed_at`). This reuses the existing `createStepUpToken`
  operation as the proof-of-possession step rather than inventing an off-contract
  confirm route.
- A never-confirmed (PENDING) factor therefore must not authorize step-up — the
  two-state machine makes "confirmed" a first-class, queryable fact. **T2 must
  enforce that step-up only accepts an ACTIVE factor.** (Left as T2's guard, per the
  brief.)

Re-enrollment: a member re-enrolling a still-PENDING factor re-issues the challenge
on the SAME row (rotating the TOTP secret) — so an abandoned enrollment can be
retried without tripping the unique constraint. A duplicate of an already-**ACTIVE**
factor is refused **409 FACTOR_EXISTS** (a confirmed credential is never silently
overwritten). Unsupported/unknown `factor_type` (incl. BIOMETRIC) -> **422
VALIDATION_FAILED**. Missing token -> 401 (via `get_current_member`).

## How SMS is mocked

`app/adapters/sms/port.py::SmsSender.send_verification_code(*, phone_number, code)`
is the port (provider-neutral; no Mongolian gateway pinned — a procurement decision,
same posture as the ХУР/XYP eKYC port). `mock.py::MockSmsSender` records every
delivered `(phone_number, code)` in `.sent` (and `.last_code`) so tests read back the
exact code; `unavailable=True` drives the `SmsDeliveryError` -> 502 branch. Injected
via the `get_sms_sender` dependency (default = a fresh `MockSmsSender`), overridable
in tests.

**Security choice:** the SMS one-time code is delivered ONLY over the port; the HTTP
`binding_challenge` returns a masked confirmation `SMS_CODE_SENT:***0001`, NOT the
code (returning it would defeat the out-of-band factor). Tests assert the raw code is
absent from the response.

## Tests — and the security property each proves

`tests/test_mfa_enrollment.py` (TestClient, `DevRsaSigner` tokens for seeded members
A/B, in-memory SQLite, `get_session`/`get_token_verifier`/`get_secret_cipher`/
`get_sms_sender` overridden; no real DB/IdP):

1. `test_totp_enroll_returns_challenge_and_stores_ciphertext` — **secret-at-rest**:
   201 + otpauth challenge; the stored `secret_ciphertext` != the plaintext seed and
   does not contain it; decrypting it (same key) returns the seed (non-vacuous); the
   seed is a working TOTP secret; row is PENDING (never auto-confirmed).
2. `test_totp_enroll_owned_by_caller_only` — **binding/IDOR**: the factor's
   `member_id` is the caller's (token subject), not B's.
3. `test_duplicate_active_factor_is_409` — **no overwrite of a confirmed factor**:
   seeding an ACTIVE TOTP factor then re-enrolling -> 409 FACTOR_EXISTS.
4. `test_reenroll_pending_totp_reissues_same_row` — **per-(member,type) uniqueness**:
   two PENDING enrollments return the same `enrollment_id` with a rotated challenge.
5. `test_sms_enroll_drives_mock_sender` — **out-of-band SMS**: exactly one 6-digit
   code delivered to the member's phone via the mock; the raw code is NOT in the
   response; no TOTP secret persisted for SMS.
6. `test_biometric_factor_type_is_422` — **only server-verifiable factors persist**.
7. `test_enroll_requires_auth` — **auth required** (401 without a token).

Notes on the tooling gates:
- **ruff**: the project's model files use `Mapped[Optional[...]]` (required because
  the code runs on Python 3.9, where SQLAlchemy eval's the annotation at mapper-config
  time — `X | None` fails on 3.9). The repo's ruff gate is the DEFAULT rule set
