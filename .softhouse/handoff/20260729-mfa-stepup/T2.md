## The step-up token design

**Opaque + DB single-use (not a stateless JWT).** The token is a 256-bit random
value (`secrets.token_urlsafe(32)`). Consumption is a DB fact (`consumed_at`), so
single-use is enforced by row state, not a JTI dance.

**Hash-only storage.** Only `sha256(token)` is persisted (`step_up_token.token_hash`,
UNIQUE). The plaintext is returned to the client exactly once and is never stored,
logged, or recoverable — a leaked DB row yields no usable token (same posture as
`onboarding_application.resume_token_hash`). SHA-256 (not a slow password hash) is
right here because the token is high-entropy random, not a guessable secret; the
store only needs to be non-reversible. `hash_step_up_token` is the single hashing
seam, shared by the minting service and `require_step_up`.

**Member binding.** `member_id` is the minting member. `require_step_up` refuses a
token whose `member_id != get_current_member`, so a token minted for A can never
authorize an action for B. The atomic consume UPDATE *also* carries
`member_id = :caller` in its WHERE, so binding is enforced twice (check + guarded
write).

**Expiry.** `expires_at = now + 5 min` (`STEP_UP_TTL`), returned to the client.
Rejected once past, whether or not consumed. (Checked in Python for the error code,
and again in the consume UPDATE's `expires_at > now` guard.)

**Action binding (optional).** `requested_action` (nullable) scopes a token to one
operation when set. `createStepUpToken` derives it from a conventional
`action_context.action` string; a NULL means a general assertion accepted by any
gated op. `require_step_up("revokeDevice")` enforces the match only when the token
is scoped — a general token passes, a token scoped to a *different* action → 403.

**Single-use consume is atomic.** `StepUpTokenRepository.consume` is a conditional
`UPDATE ... SET consumed_at=:now WHERE id=:id AND member_id=:m AND consumed_at IS
NULL AND expires_at > :now`; `rowcount == 1` means *this* call spent it. A replay
(or a concurrent race) matches zero rows → refused. The dependency commits the
consumption immediately, so the token is spent even if the guarded operation then
fails — single-use is not conditional on the action succeeding.

## Lockout (brute-force protection)

State lives on `mfa_factor`: `failed_attempts` (int, server default 0) and
`locked_at` (nullable). `MAX_FAILED_ATTEMPTS = 5`, `LOCKOUT_DURATION = 15 min`.

- Each wrong `factor_response` increments `failed_attempts`; the attempt that
  reaches the threshold sets `locked_at` and returns **423 FACTOR_LOCKED**. Wrong
  attempts below the threshold return **401 STEP_UP_FAILED**.
- A correct code resets the counters (and, if PENDING, activates the factor).
- While locked, even a correct code is refused (423). A lock older than
  `LOCKOUT_DURATION` auto-clears on the next attempt — no permanent lock-out with
  no unlock path.
- **Critical detail:** the router commits the lockout bookkeeping on the *error*
  path too. Without that commit the increment would roll back with the request
  session and the counter could never accumulate — brute-force protection would be
  a no-op. Only the lockout state is committed on failure (no token is minted).

## The TOTP window / binding

Reused verbatim from T1: `app.auth.mfa.verify_totp` (pyotp, constant-time compare,
`TOTP_VALID_WINDOW = 1` → ±1 step, no wide drift). The secret is decrypted from
`SecretCipher` in-memory only to verify; never logged. Step-up verifies against the
member's own TOTP factor (the server-verifiable one; the SMS OTP is not persisted at
rest, per T1). **Binding decision (per T1):** the first correct code flips a PENDING
factor to ACTIVE (`status=ACTIVE`, `confirmed_at`), so confirmation happens *through*
the first step-up — there is no off-contract confirm route. An absent / never-correct
factor can never mint (minting requires a correct code), satisfying "a never-confirmed
factor cannot authorize step-up".

## require_step_up

Composed with `get_current_member` (FastAPI resolves it once per request, so the
route body and the dependency see the same member). Reads `X-Step-Up-Token`
(the root.yaml `stepUpAssertion` apiKey header). Missing → **401 STEP_UP_REQUIRED**.
Absent / foreign-owner / expired / already-consumed all collapse to a uniform
**401 STEP_UP_FAILED** (no token enumeration, no owner leak). A scoped/action
mismatch → **403 STEP_UP_ACTION_MISMATCH**. On success it consumes atomically and
commits, returning the `StepUpToken`.

## revokeDevice wiring + IDOR

`DELETE /api/v1/auth/devices/{id}` depends on `get_current_member` AND the
module-level `require_step_up("revokeDevice")` singleton (hoisted to module scope so
the factory call is not an argument default — avoids ruff B008). The device id comes
from the path but is ALWAYS scoped to `member.id` in
`DeviceService.revoke_device` → `DeviceBindingRepository.get_owned(member_id, id)`.
A device that does not exist OR belongs to another member both resolve to `None` →
the same **404 NOT_FOUND** (`DeviceNotFound`), so an IDOR probe and a genuine miss
are indistinguishable — no cross-member reveal. Revoke is **idempotent**: an
already-REVOKED owned device returns 200 REVOKED unchanged (the contract defines no
distinct already-revoked error; the terminal state is identical). The contract's
409 LAST_DEVICE is declared but not triggered in this slice.

## Which attack each test proves (`tests/test_stepup.py`, 11)

1. `test_enroll_then_confirm_via_step_up_happy_path` — enroll→confirm-via-step-up→
   mint: PENDING flips ACTIVE on the first correct code; only the token HASH is
   stored (plaintext in no row); token unconsumed at mint.
2. `test_wrong_totp_is_rejected_and_mints_nothing` — a wrong code → 401 and mints
   NO token (guessing never yields a credential).
3. `test_absent_factor_cannot_mint` — no enrolled factor → 401 (never-enrolled
   authorizes nothing).
4. `test_lockout_after_n_failures_returns_423` — 5 wrong codes lock the factor
   (423); even a subsequently-correct code is refused (lockout is real).
5. `test_revoke_device_without_step_up_is_rejected` — revokeDevice with no
   `X-Step-Up-Token` → 401 STEP_UP_REQUIRED; device untouched.
6. `test_revoke_device_with_valid_step_up_succeeds` — valid token → 200 REVOKED;
   device actually revoked.
7. `test_step_up_token_is_single_use` — first use 200, REPLAY of the same token →
   401 (consumed).
8. `test_expired_step_up_token_is_rejected` — an unconsumed but EXPIRED token → 401;
   device untouched.
9. `test_token_minted_for_a_rejected_for_b` — member binding: A's token presented by
   B (against B's own device) → 401; A's token stays unconsumed (a foreign
   presentation does not spend it).
10. `test_step_up_token_scoped_to_other_action_is_rejected` — action binding: a token
    scoped to a different action → 403 STEP_UP_ACTION_MISMATCH; device untouched.
11. `test_revoke_device_idor_returns_404` — IDOR: A holds a VALID token but targets
    B's device id → 404; B's device stays ACTIVE (no cross-member revoke).

Plus `tests/test_devices.py::test_revoke_device_requires_step_up` (the route is
mounted but step-up-gated).

## Key-management caveat (inherited)

The step-up token store is hash-only and needs no encryption key. The TOTP secret
decryption still uses T1's `SecretCipher` (Fernet, `DCB_MFA_ENC_KEY`,
operator-supplied, fail-closed, KMS in production — see T1.md). Nothing in this
slice logs a token, a secret, or a key.
