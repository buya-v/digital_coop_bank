## Fix (1) — Promotion row-lock (idempotent KYC promote, no 500)

**Failure prevented:** two concurrent `getKycStatus` polls on an IN_PROGRESS draft
that both observe the register returning APPROVED both call `_promote` → two
`Member` INSERTs → the second violates the `registration_number` / `member_id`
UNIQUE constraint → uncaught `IntegrityError` → HTTP 500. (Previously only
backstopped by DB uniqueness.)

**Change:**
- `app/repositories/onboarding.py` — new `get_by_resume_token_hash_for_update()`:
  `select(...).with_for_update().execution_options(populate_existing=True)`. The
  `FOR UPDATE` row lock serializes the second poll behind the first (Postgres);
  `populate_existing=True` forces the already-identity-mapped draft to be
  refreshed from the freshly-locked row (so the caller re-reads the committed
  APPROVED, not a stale in-memory IN_PROGRESS).
- `app/services/kyc.py` `get_status()` APPROVED branch — before promoting, take the
  lock and re-read: if the draft is already APPROVED (a concurrent poll won the
  race and froze it), return the recorded APPROVED **without** re-promoting;
  otherwise promote. Exactly one Member; DEC-4 (no Member on reject) untouched.

**SQLite note:** SQLite ignores `FOR UPDATE`, so the block-and-serialize behaviour
is Postgres-only — but the re-read idempotency guard still yields exactly one
Member on either backend, which the test asserts. `with_for_update` presence is
confirmed for Postgres by a dialect-compile assertion.

**Tests (`tests/test_kyc.py`):**
- `test_concurrent_approved_polls_promote_exactly_one_member` — deterministically
  simulates the race (session A loads the draft while IN_PROGRESS; session B
  promotes+commits; session A's poll then runs on its stale view, entering the
  guarded promote branch). Asserts exactly 1 Member, 1 KycSubmission, no error.
  Proven non-vacuous: neutering the re-read guard **or** removing
  `populate_existing` makes it fail with the exact `IntegrityError` the fix
  prevents.
- `test_promotion_lock_query_renders_for_update_on_postgres` — confirms the
  locking select renders `FOR UPDATE` under the postgresql dialect.

## Fix (2) — CLOSED-member auth + `require_active_member` (safe subset of backlog #2)

**Failure prevented:** `get_current_member` resolved ANY member regardless of
`membership_status`, so a CLOSED account could still authenticate and act.

**Change (`app/auth/deps.py`):**
- `get_current_member` now rejects a CLOSED member with the **same uniform 401**
  (code `UNAUTHENTICATED`, identical message) as an unknown subject — a CLOSED
  member is indistinguishable from a non-existent one to the caller (no
  account-status enumeration / info leak).
- New `require_active_member` dependency — composes `get_current_member`, then
  requires `membership_status == ACTIVE`; any other authenticated status
  (SUSPENDED, or a just-promoted PENDING_PAYMENT / PENDING_KYC) → 403
  `MEMBER_NOT_ACTIVE` (the code root.yaml already defines for
  `MembershipStatus != ACTIVE`). **Documented as available for future
  money/sensitive ops and applied to NO current route** — a just-promoted member
  is PENDING_PAYMENT (not ACTIVE) and must still complete onboarding / manage
  their profile, consents and devices, so those routes keep depending on
  `get_current_member`. No router was changed.

**Tests (`tests/test_auth.py`):**
- `test_closed_member_is_rejected_uniform_401` — CLOSED token → 401
  `UNAUTHENTICATED`, same message as unknown-subject. Non-vacuous (an ACTIVE
  member with the same token shape is admitted 200; mutation confirmed).
- `test_require_active_member_allows_active` — ACTIVE → 200.
- `test_require_active_member_rejects_suspended_403` — SUSPENDED authenticates
  (`/probe/me` 200) but `/probe/active` → 403 `MEMBER_NOT_ACTIVE`.
- `test_require_active_member_rejects_pending_payment_403` — PENDING_PAYMENT
  authenticates but → 403 (the reason it must NOT gate onboarding/profile).

## Fix (3) — /ready malformed DATABASE_URL → 503, not 500 (backlog #12)

**Failure prevented:** a non-empty-but-garbage `DATABASE_URL` passes
`engine_configured()` (non-empty) but makes `create_engine()` raise
`ArgumentError` while building the engine during `/ready`'s dependency
resolution → uncaught → HTTP 500 (and risks leaking the URL/exception text).

**Change (`app/main.py`):**
- `ready_session` now builds the engine up front inside a `try` (`get_engine()`);
  on any build failure it yields a small `_EngineUnavailable` sentinel whose
  `execute()` raises, so `/ready` reports the failure through its **existing**
  error path → 503 `{status: unready, db: error}`, exception text never leaked —
  consistent with the runtime-liveness-failure path. Happy/unconfigured paths
  unchanged.

**Test (`tests/test_ready.py`):**
- `test_ready_malformed_database_url_returns_503_not_500` — monkeypatches the
  engine build to raise `ArgumentError` (as a malformed URL does) and asserts
  `/ready` → 503 unready/error with the URL detail absent from the body.
  Non-vacuous: reverting the guard makes the `ArgumentError` propagate (the 500).
