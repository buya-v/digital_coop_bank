# T3 — expose + edit `preferred_language` on the member profile

**Branch:** `softhouse/T3-preferred-language`
**Date:** 2026-08-03
**Epic:** EP-1 identity — member self-service profile (04 §3.1)

## Problem

The `Member` ORM already carries `preferred_language` (`String(35)`, default `mn`,
`app/models/membership.py:93`), but it was absent from the `MemberProfile`
contract and from both profile endpoints — so a member could neither read nor
change their preferred UI language. Cyrillic-Mongolian (`mn`) as the default is a
market non-negotiable (CLAUDE.md). No schema/migration/money change was needed —
only surfacing an existing column.

## Change summary

Reused the established profile pattern (service owns editability/validation,
router owns transaction boundary + HTTP mapping, identity from `get_current_member`
only). No member id in any path or body, so the IDOR class stays excluded by
construction.

### 1. OpenAPI schema (`backend/openapi/schemas/ep1-identity.yaml`)

- Added `preferred_language` to **`MemberProfile`** (returned by `GET /members/me`):
  `type: string`, `pattern: '^[A-Za-z]{2,3}(-[A-Za-z0-9]{2,8})*$'`, `maxLength: 35`,
  `default: mn`. BCP-47-ish tag; documented that an invalid value yields 422.
- Added `preferred_language` to **`ProfilePatchRequest`** (editable set), same
  pattern + `maxLength: 35`, noting it is not KYC-relevant.

### 2. Editable-set change (`backend/app/services/profile.py`)

- Added `preferred_language` to `EDITABLE_FIELDS`.
- Added `NON_REVERIFYING_FIELDS = {preferred_language}` — a UI preference is not
  KYC-relevant, so editing it alone does **not** set `reverification_required`
  (`apply_update` excludes it from the change computation).
- Added `ProfileFieldInvalid` (422) + `_validate_preferred_language`: rejects a
  non-str, a value > 35 chars, or one that fails the BCP-47-ish regex. Validation
  runs in the validate-then-apply phase, so a rejected PATCH leaves the row
  untouched. Error code `PREFERRED_LANGUAGE_INVALID`.
- The read-only fields (`legal_name` / `mrz_name_latin` / `registration_number` /
  `member_id`) still 422 — unchanged.

### 3. Endpoint conformance (`backend/app/api/routers/members.py`)

- `MemberProfile` pydantic gains `preferred_language: str = "mn"`; `_to_profile`
  projects `member.preferred_language`; `getMyProfile` now returns it.
- `ProfilePatchRequest` pydantic gains `preferred_language: Optional[str]`;
  `updateMyProfile` maps `ProfileFieldInvalid` → 422 with the field's code.

### 4. Tests (`backend/tests/test_profile.py`)

- GET returns `preferred_language` (seeded default `mn`).
- PATCH `en` persists, reflected on a later GET, and `reverification_required` is
  `False` (not KYC-relevant).
- PATCH accepts a full BCP-47-ish tag (`mn-Cyrl-MN`).
- PATCH an invalid value → 422 `PREFERRED_LANGUAGE_INVALID`, stored value
  unchanged — parametrized over `english`, `e`, `mn_MN`, `not a language!`,
  `123`, `` (empty).
- IDOR: a language PATCH via A's token never touches B.
