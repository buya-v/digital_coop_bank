## The problem this closes

Before T4 the SMS factor could ENROLL (a code was sent via the mock port) but had
**no server-side verify** — only TOTP could mint a step-up. An SMS factor's
`factor_response` is a one-time code SENT to the member, not a stored seed the
client can regenerate. So the code has to be **issued as a challenge** and
remembered server-side long enough to verify one response. T4 adds that.

## Design

An SMS factor now carries a short-lived, hash-only, single-use **challenge** on its
`mfa_factor` row:

- **Enrollment** (`_prepare_sms`) already sent a code; it now also ARMS that code
  as the first challenge (stores its hash + expiry). The member's first correct
  step-up response verifies it and binds the factor ACTIVE — same binding rule as
  TOTP.
- **`createStepUpToken`** verifies the submitted code against the armed challenge.
  Factor resolution: an SMS factor with an OUTSTANDING (armed + unexpired)
  challenge is verified as SMS; otherwise TOTP. So a TOTP-only member is unchanged;
  an SMS member is targeted only inside the code's live window. A correct code
  BURNS the challenge (single-use).
- **`createMfaChallenge`** (the ADDED endpoint) re-issues a fresh code — needed
  when the binding code expired, or before each step-up on an ACTIVE SMS factor.

### Contract addition (minimal, well-formed) — why

The base contract has createMfaEnrollment + createStepUpToken but **no
per-request SMS code-issuance step**. TOTP needs none (the authenticator derives
codes from the seed); SMS must be SENT before each step-up. So exactly one new
operation was added, mirroring the existing MFA surface:

- `POST /api/v1/auth/mfa/challenges` — `createMfaChallenge` → 201
  `MfaChallengeResponse`.
  Request `MfaChallengeRequest { factor_type }` (only SMS is challengeable).
  Response `MfaChallengeResponse { challenge_id, delivery, expires_at }` — all
  NON-secret; the code never appears in the body.
  Errors: 401 (Unauthorized), 404 (no enrolled SMS factor), 422 (TOTP/unsupported),
  423 (FACTOR_LOCKED), 429 (TooManyRequests), 502 (SMS_DELIVERY_FAILED) — the same
  error vocabulary the enrollment path already uses. `openapi/validate.py` PASSES
  (173 paths · 193 operations · 306 schemas). No undocumented behaviour: no field
  was added to the existing `StepUpRequest` — SMS-vs-TOTP is resolved server-side
  from the existing `factor_response`.

### Column addition (model + migration in LOCKSTEP)

`mfa_factor` gained two nullable columns (both NULL for TOTP and for an SMS factor
with no outstanding challenge), placed after `locked_at`:

- `sms_challenge_hash VARCHAR(128)` — SHA-256 hex of the issued code (never the
  plaintext).
- `sms_challenge_expires_at TIMESTAMP WITHOUT TIME ZONE` — the code's short expiry.

The existing `failed_attempts` / `locked_at` are REUSED for the SMS lockout — no
new attempt counter. `check_migration` PASS (146 = 146 DDL statements, lockstep).

## Security controls (the reviews will attack)

- **Hash-only, out-of-band.** The code is delivered ONLY via the SMS port; the
  response carries a masked `SMS_CODE_SENT:***tail`, never the code. Only its
  SHA-256 hash lands on `sms_challenge_hash` — plaintext is never stored, logged,
  or returned. SHA-256 (not a slow KDF) is deliberate and documented in
  `hash_sms_code`: hash cost is not the control for a low-entropy 6-digit code —
  the compensating controls below are. Verify uses `hmac.compare_digest`
  (constant-time).
- **Single-use.** A correct code CLEARS `sms_challenge_hash`/`_expires_at`, so a
  replay of the same code finds no challenge and fails (proven non-vacuously).
- **Short expiry.** `SMS_CHALLENGE_TTL = 5 min`; an expired challenge is refused
  even with the correct code.
- **Lockout (same 423 as TOTP).** Wrong SMS codes increment `failed_attempts`; at
  `MAX_FAILED_ATTEMPTS` the factor LOCKS (423) for `LOCKOUT_DURATION`. Online
  guessing is thus capped at a handful of tries against a 10**6 space.
- **Lockout cannot be bypassed by re-arming.** `createMfaChallenge` refuses (423)
  while the factor is locked and does NOT touch the lockout counters; re-enrollment
  likewise does not reset them.
- **Step-up token guarantees unchanged.** The minted token is still the opaque,
  hash-only, member-bound, single-use, 5-min `step_up_token` from T2 — SMS just
  feeds the same mint path.
- **IDOR excluded by construction.** Both new/changed endpoints take the member
  from `get_current_member`; no member id from path/body.

## Tests — `backend/tests/test_stepup.py` (each attack non-vacuous)

- `test_sms_enroll_issues_challenge_out_of_band` — code is delivered via the mock,
  NOT in the HTTP body; row armed PENDING, hash-only (hash != code), no seed.
- `test_sms_step_up_with_code_succeeds_and_mints_single_use_token` — the OOB code
  binds the factor ACTIVE + mints a token stored hash-only; challenge then cleared.
- `test_sms_wrong_code_is_rejected_and_mints_nothing` — wrong code → 401, zero
  tokens.
- `test_sms_lockout_after_n_failures_returns_423` — N wrong codes → 423; the
  correct code is then also refused (423).
- `test_sms_challenge_is_single_use_replay_fails` — replay of a spent code → 401;
  only one token ever minted.
- `test_sms_challenge_expires` — force the challenge into the past → the correct
  code is refused (401), zero tokens.
- `test_create_mfa_challenge_reissues_a_fresh_code` — new code works, superseded
  code stops working; new code not in body.
- `test_create_mfa_challenge_rejects_totp` — TOTP challenge → 422.
- `test_create_mfa_challenge_without_enrolled_sms_is_404` — no SMS factor → 404.
- `test_create_mfa_challenge_refuses_while_locked` — locked factor cannot be
  re-armed (423); no fresh code sent.
