## Design

**Why migration-free is possible.** Every SMS send (both `_prepare_sms` and
`MfaChallengeService.issue`) already writes
`factor.sms_challenge_expires_at = now + SMS_CHALLENGE_TTL` on send. Since
`SMS_CHALLENGE_TTL` is a fixed constant, `last_sent_at` is recoverable exactly as
`sms_challenge_expires_at - SMS_CHALLENGE_TTL` with no precision loss and no new
column. `_enforce_sms_resend_interval` does exactly that:

```python
def _enforce_sms_resend_interval(prior_expires_at, now):
    if prior_expires_at is None:
        return                              # never sent before -> never limited
    last_sent_at = prior_expires_at - SMS_CHALLENGE_TTL
    if now - last_sent_at < SMS_RESEND_INTERVAL:
        raise SmsRateLimited()
```

`SMS_RESEND_INTERVAL` (60s) is required to stay strictly below `SMS_CHALLENGE_TTL`
(5 min) — satisfied by construction (60s < 300s) and documented at the constant's
definition.

**Per-factor, not per-endpoint.** Both send call sites (`_prepare_sms` and
`MfaChallengeService.issue`) read/write the SAME `sms_challenge_expires_at` column
on the SAME `MfaFactor` row, so the interval is enforced across BOTH endpoints for
a given factor — matches the brief's "a per-factor minimum-resend-interval" and
the vulnerability description, which treats both call sites as one shared
cost/bombing vector on the same factor.

**First-send exemption.** `existing is None` (brand-new enroll) never reaches the
check at all — the SMS is sent unconditionally on that branch. An existing row
with `sms_challenge_expires_at is None` (never had an outstanding/prior
challenge — e.g. a directly-seeded ACTIVE SMS factor never yet challenged) also
always passes, per `_enforce_sms_resend_interval`'s `None` short-circuit.

**Ordering on the challenge path (423 before 429).** `issue()` still checks
`factor.locked_at`/`LOCKOUT_DURATION` FIRST, unchanged; the new rate-limit check
runs strictly after that and before `generate_sms_code()`. A locked factor that
also happens to be inside the resend window (which it always will be, since a
lock only sets in after a step-up failure that itself required a prior send)
returns 423, never 429. Verified by
`test_locked_sms_factor_challenge_is_423_not_429`, which seeds BOTH conditions
simultaneously to force the ordering to matter.

**Lockout discipline preserved.** `_enforce_sms_resend_interval` and
`SmsRateLimited` never read or write `failed_attempts`/`locked_at` — verified by
assertions in the two "immediate resend" tests that these fields are unchanged
(`0` / `None`) after a 429.

**No float anywhere.** All arithmetic here is `datetime.timedelta` /
`datetime.datetime` subtraction — no numeric/monetary types touched, no floats
introduced.

## Tests

All added to `backend/tests/test_mfa_enrollment.py` (7 new tests, appended after
the existing `test_enroll_requires_auth`), plus one new helper
`_seed_sms_factor` (mirrors the existing `_seed_member`/`_factor` pattern) and one
new helper `_age_sms_challenge` used to simulate elapsed time by directly rewriting
`sms_challenge_expires_at` in the DB — **no `time.sleep` anywhere**, per the
instruction.

1. `test_sms_enroll_immediate_resend_is_429_and_sends_no_second_sms` — first SMS
   enroll succeeds (201, 1 SMS sent); an immediate second enroll for the same
   member/factor returns 429 with body `error.code == "RATE_LIMITED"` and the
   mock's `sent` list is STILL length 1 (proves the rate limit fires before the
   SMS port is called, not after). Also asserts `failed_attempts == 0` and
   `locked_at is None` after the 429 (lockout discipline untouched).
2. `test_sms_enroll_resend_after_interval_elapses_succeeds` — after the first
   enroll, ages `sms_challenge_expires_at` back by
   `SMS_RESEND_INTERVAL + 5s` via `_age_sms_challenge`, then a second enroll
   succeeds (201) and the mock's `sent` list grows to 2.
3. `test_sms_challenge_first_send_succeeds` — seeds an ACTIVE SMS factor with
   `sms_challenge_expires_at=None` (never challenged before) and proves
   `POST /auth/mfa/challenges` succeeds 201 on the very first call.
4. `test_sms_challenge_immediate_resend_is_429_and_sends_no_second_sms` — same
   seed, first challenge 201 (1 SMS sent), immediate second challenge 429
   `RATE_LIMITED`, still only 1 SMS sent; `failed_attempts`/`locked_at` untouched.
5. `test_sms_challenge_resend_after_interval_elapses_succeeds` — first challenge
   201, ages the timestamp, second challenge 201, 2 SMS sent total.
6. `test_locked_sms_factor_challenge_is_423_not_429` — seeds a factor with
   `locked_at=now` AND `sms_challenge_expires_at=now` simultaneously (both a lock
   AND a rate-limit condition are true), asserts the response is 423
   `FACTOR_LOCKED`, not 429 — proves the lock check still runs first. Also
   asserts zero SMS were sent (refused before send in either case).
7. `test_totp_enrollment_unaffected_by_sms_rate_limit` — two immediate,
   consecutive TOTP enrollments both return 201 (TOTP never touches
   `sms_challenge_expires_at` or the SMS port at all); asserts zero SMS sent.

Existing tests already covering "a first SMS enroll succeeds" and "the code is

`tests/test_stepup.py::test_create_mfa_challenge_reissues_a_fresh_code` (line
690) does: enroll an SMS factor via `POST /auth/mfa/enrollments` (which sends
code #1 and sets `sms_challenge_expires_at`), then IMMEDIATELY calls
`POST /auth/mfa/challenges` on the same factor expecting a fresh code #2 (201).
With the new rate limit, that second call is now correctly rate-limited (429
`RATE_LIMITED`) because both send call-sites share the same factor's
`sms_challenge_expires_at`, and less than `SMS_RESEND_INTERVAL` (60s) elapsed
between the two calls in the test.

This is not a bug in the new logic — it is the exact vulnerability described in
the task brief being closed: "both call `self._sms.send_verification_code(...)`
on every request with no minimum interval" is explicitly framed as ONE shared
per-factor vector across BOTH `_prepare_sms` and `MfaChallengeService.issue`. The
old test's scenario (enroll, then immediately re-challenge the same factor) is
now exactly the case the rate limit exists to block.

I could not resolve this within scope. Two options for whoever picks this up:
1. Update `test_create_mfa_challenge_reissues_a_fresh_code` to age
   `sms_challenge_expires_at` between the enroll and the challenge call (the
   same technique I used in the new tests — `_age_sms_challenge`-style, no
   `time.sleep`) before asserting 201.
   OR
2. Revisit whether the rate limit should be scoped narrower (e.g. per-endpoint
   rather than per-factor) — but note the task brief's vulnerability framing
   and the "per-factor" wording in the REQUIRED FIX section both point at the
   shared-column design I implemented, so I believe option 1 is correct and
   this failing test is a pre-existing test that needs updating to match the new,
   intentionally stricter security behavior — not a defect in this change.

I flagged this rather than silently editing `test_stepup.py` myself, since it is
outside my declared SCOPE.
